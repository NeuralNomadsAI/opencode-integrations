# OpenCode for Blender

`@neuralnomads/opencode-blender` lets OpenCode read and change the scene open in Blender 5.3 or later. It is a `native` integration: the **OpenCode Link** add-on runs an authenticated host inside Blender, and the plugin sends it typed, revision-checked batches, fixed inspection and render programs, and (asking each time) Python code. No Blender documentation is bundled: the plugin asks the running Blender what it exposes and links the official documentation of its version.

> **Status: preview (draft 0.2, `spec: 0`, RPC contract 1).** Not published to npm yet.

## Installation

### Any OpenCode client

1. Add the plugin to the `plugins` list of your **global** OpenCode configuration (`~/.config/opencode/opencode.json`). Native integrations are installed in the global configuration only.

   ```jsonc
   {
     "plugins": ["@neuralnomads/opencode-blender@^0.4"]
   }
   ```

   With options (all optional, see [Options](#options)):

   ```jsonc
   {
     "plugins": [{ "package": "@neuralnomads/opencode-blender@^0.4", "options": { "hostInspectionDir": "/path/to/extensions/user_default" } }]
   }
   ```

2. Install the add-on: ask OpenCode to run `blender_install_host` (it asks for permission), or install `host/blender/opencode_link-<version>.zip` from the package with Blender's **Preferences ▸ Get Extensions ▸ Install from Disk**. The add-on is installed on the computer that runs OpenCode, in the user extensions folder of the newest Blender 5.3 or later started there.
3. In Blender, enable **OpenCode Link** (Preferences ▸ Add-ons). While it is enabled, the session is offered to OpenCode, at every start included; disabling it withdraws the offer.
4. In OpenCode, use any Blender tool: with one Blender open and attached to no other conversation, the first call attaches it to this conversation. With several, `blender_hosts` lists them and `blender_hosts` with `attach` attaches one (it asks for permission).

### In CodeNomad

The **Plugins** section lists OpenCode for Blender as an integration: its version, whether the add-on is installed and up to date, and whether the conversation is attached; its menu installs or updates the add-on after a confirmation and detaches the conversation. **Plugins ▸ Add** also accepts the package name.

## How it works

- **Discovery and consent.** While OpenCode Link is enabled, the add-on listens on `127.0.0.1` on a random port with a random 256-bit token kept in memory, and offers the session to every OpenCode service registered for your user (or to one: the add-on setting _OpenCode service_). Offers last 15 seconds and are renewed every 5 seconds.
- **Attachment.** A conversation acts on the Blender attached to it. The only offered Blender, compatible and attached to no conversation, attaches itself at the conversation's first Blender call, without asking; otherwise `blender_hosts` with `attach` asks the `blender_attach` permission. Opening another file in Blender replaces the offer: the conversation attaches again the same way.
- **Which Blender.** `blender_hosts` and `blender_context` name the Blender this conversation acts on (`attached_to`: offer and label). Other conversations attaching or detaching other Blenders, or Blenders appearing, never make this conversation's ownership unverifiable; a permission prompt is refused only when this conversation's own Blender changed meanwhile.
- **Across an OpenCode restart.** The plugin keeps each conversation's attachment in its storage (the Blender's offer key only as a SHA-256 digest, with the label; never a token, port or script handle). When the same Blender offers itself again after a restart, the conversation is attached back without asking, once its ownership is verified at its Location; never inside a read. A kept attachment lasts while its Blender is offered and two minutes after it stops; detaching removes it at once. A Blender restarted itself is a new offer: the conversation attaches again as above.
- **Upgrading without restarting OpenCode.** A daemon that loads a newer version of the plugin without restarting can keep the older one in memory. Each version keeps its own list of offered Blenders, named after the add-on versions it accepts, so a Blender is always judged by the version that lists it; it offers itself again within 5 seconds.
- **The working method.** When a conversation attaches a Blender, a short method joins it (an instructions entry, about 200 tokens): read the Blender version first, ask Blender itself (`blender_inspect`) before writing code in an area that changed recently, verify each step by its result (`blender_verify` for anything that renders), and write down what you discover.
- **Session binding.** Clients read `bindingRead({ sessionID })` at the session's current OpenCode Location: `attached` identifies its live offer and safe label, `none` confirms a verified session without a binding, and `unknown` keeps the state unverified. `status_changed {}` invalidates the read; `detachHost({ sessionID })` detaches. See the [draft 0.2 RPC contract](../../../spec/rpc-contract.md).

Behaviour to know:

- **Primitive `size`** (default 1 m) is a cube's edge, a plane's side, a uv_sphere's diameter, a cylinder's diameter and height, a cone's base diameter and height; `depth` gives a cylinder's or cone's height apart. A text's `size` is its font size.
- **`fit_height`** scales Z only by default (`scale_axes: "uniform"` keeps the proportions, and says that X and Y were scaled too); it refuses a tilted object in Z mode; without `height` it scales nothing. The result names the axes and the factor. With `frame` it measures the deformed pose at that frame and `key` keys the result there.
- **Rotations** are written in the holder's own mode: Euler angles in its order as given (360° stays 360°, so a full turn can be keyed); another order or a quaternion becomes the equivalent nearest the current angles. A quaternion or axis-angle holder keeps an orientation only and says so for 180° or more. A linear full turn: `insert_key` with `interpolation: "LINEAR"` on both keys.
- **`reach`** solves a two-bone chain once and writes the pose (no IK constraint is left): the lower bone's tail on the target, the elbow toward `pole` (by default the side it bends to now), the end bone turned like an object or bone target; at `frame` it keys the chain's rotations. A target out of reach is refused and undone, with the chain's length.
- **`switch_parent`** keeps one anchor empty and one Copy Transforms constraint per switch, named `OC parent f<frame> <parent>`; its own keys no longer move the object after a switch.
- **`insert_key`** and **`delete_keys`** take an RNA path on the object, its data or its shape keys (`owner`); `delete_keys` removes keys by position from the last and an F-curve left empty.
- **`set_parent`** with `keep_transform` evaluates the scene first, so objects created or moved earlier in the batch keep their world transform, and keeps the object's own values (Blender's Parent, Keep Transform).
- **`delete`** frees the names at its place in the batch: a later `create_object`, `duplicate` or `rename` gets that exact name, and the new mesh the deleted mesh's name when only the deleted object used it. The deleted objects leave the document when the batch succeeds, with the data only they used.
- **`duplicate`** copies a hierarchy into the originals' collections, keeps each child's parenting, points constraints at the copies and shares materials and actions; `linked` also shares the data. A `name` or `suffix` another object holds is refused before anything runs.
- **`set_material`** creates a Principled material when no material has that name, or sets the values of an existing one; a value Blender would clamp fails the batch, which is restored.
- **`scene_settings`** never lets Blender push the other end of the frame range: one end crossing the other is refused. `fps` 23.976 sets fps 24 and its base.
- **`shift_keys`** moves keys with both handles (or deletes them) in the action slot the object uses (Blender 5 layered actions); a key landing on one that does not move is refused.

## Code execution

`blender_execute_code` runs Python in Blender with your rights: it can read and write files, start processes and reach the network. The add-on lists it while it is enabled, and **every run asks the `blender_execute_code` permission** ("ask" unless you allow it in OpenCode's permission settings); a refused run executes nothing. A run that changes the scene is one undo step; a failing one is undone. Blender keeps linked data outside its undo (a linked library, the brush a sculpt or paint mode links): it is named in `restoration.kept_linked`, unused and not saved. When an undo cannot be proven, OpenCode Link is **quarantined**: reads, `blender_verify`, `blender_inspect` and `read_only` code still run, changes wait; `blender_context` shows `quarantine.may_have_changed`, and once you checked it, `blender_context` with `release_quarantine` (that read's revision) lifts it, as does Reset in the add-on's panel. A long script can be a file (`path`): it is read as written, with no escaping through a JSON or JavaScript string, and its tracebacks name the file. See [`SECURITY.md`](../../../SECURITY.md).

## Blender limits

- Blender 5.3 or later; edits run in Object mode only.
- Two conversations may attach the same Blender: each batch is checked against the document's revision.
- The code-change fingerprint that keeps the revision current does not read mesh vertices, modifier and node values or settings below one nested level. A `read_only` run is judged by its content instead (poses, mesh vertices, shape key values, constraint influences, material node values): one that puts everything back is no change.

## Earlier installation

A `blender` plugin file in the global configuration, or a listener answering the earlier bridge's ping on port 9876, is reported as `legacy_install` in `status`. Remove it: both would compete with this plugin.
